Core Web Vitals: what a page cache changes, and what it does not

LCP, INP and CLS are field metrics measured in the browser, and a page cache only touches the part of them that happens on the server. That is still the largest single component on most WordPress sites — the time before the browser receives anything — but knowing the boundary stops you buying plugins that cannot help.

INP — mostly not a caching problem

Interaction to next paint is about JavaScript on the page. A heavy slider or a chat widget will dominate it regardless of caching. Measure with JavaScript disabled to see the difference; if INP is fine without scripts, the fix is choosing fewer of them.

CLS — layout stability, not speed

Layout shift comes from images without dimensions, late fonts and injected banners. Caching changes when the document arrives, not how it lays out. Set width and height on images and reserve space for anything that loads late.

LCP — improved by the cache and by images

The largest element is usually a hero image or the H1. A cached page shortens the wait before the HTML arrives, and correct image sizing and modern formats shorten what follows. Granite Edge Cache does both: it serves cached HTML and converts uploads, so the LCP request is smaller and starts earlier.

The honest test is a stopwatch, not a score. Load the same page five times with the plugin disabled and five times with it enabled, on the same network, and compare the median. Then check the cache page for a miss count that keeps rising on pages you never visit - that is usually a query string, a cookie, or a form that should have been excluded.

Granite Edge Cache records what it did per request: whether it served from cache, how many bytes it saved, and how long generation took. Those three values are enough to tell a working setup from one that only looks configured.

Who this is for

Granite Edge Cache fits a site on one server: a blog, a brochure site, a small shop, a club site with a thousand visits a day. It is the wrong tool for a WordPress network of fifty sites with a shared object cache cluster — that needs infrastructure, not a plugin — and it is unnecessary on a site that already serves static files from a build step.

What it does not do

It will not make a slow host fast, and it will not score well on a lab test that disables caching. It does not touch other plugins' tables, does not replace Redis, and does not promise a Core Web Vitals pass on a theme that ships six JavaScript libraries. Every claim on this page is something the plugin itself performs.

Frequently asked

Will a cache plugin fix my Core Web Vitals?

It reliably improves LCP by shortening server time and reducing image bytes. INP and CLS depend on your theme and scripts.

How long until the scores change?

Field data lags by up to 28 days because it averages real visits. Lab tools change immediately.

Do I need to keep the plugin enabled to keep the score?

Yes — the cached HTML is what the measurement saw. Disabling it returns the site to per-request rendering.
